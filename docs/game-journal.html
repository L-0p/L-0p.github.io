One Shot, Autopsy, Goals

My process using WebbGPT to create browser games, troubleshoot a problem, and understand how the code works.

Leo Fan · October 13, 2026

My starting point

I started by asking WebbGPT to make a playable game like Google Snake. I wanted to see how an idea described in a prompt could become a browser game.

The first result did not work when I tried to start it. I reported the problem and asked WebbGPT to revise the game. After that, I asked for a more complex Snake game, a tag game, and a Geometry Dash-like game.

My role: WebbGPT generated the code. I requested the games, reported the startup problem, and asked for changes. For this autopsy, I am focusing on the repaired Snake file, snake-game-fixed.html.

Stage 1 · First prompt

The first Snake game did not start

My first request was: “Can you make a playable game that is like the snake game on Google?”

The page displayed the score and instructions, but the board was blank. There was no visible snake or apple. This was the problem that led me to ask for a revision.

This showed me that receiving generated code does not automatically mean the result works. Trying the game revealed a problem that the original response did not.

Stage 2 · Revision

Asking WebbGPT to make it work

I told WebbGPT, “the game isnt working when i try to start it.” It supplied a revised version and explained changes to storage access, starting the game, and managing the game loop.

  • It wrapped localStorage access in try/catch so blocked storage would not stop the script.
  • It added click-to-start and a keyboard listener on window.
  • It tracked and canceled animation frames to prevent duplicate loops during pause and resume.

The screenshot shows a visible improvement from the blank first version. WebbGPT proposed the causes of the failure; my original report did not establish which cause affected my computer.

Stage 3 · More complexity

Snake Deluxe

Next, I asked WebbGPT to make the game more complex. The new version introduced Easy, Normal, and Hard modes, levels, stone obstacles, golden apples, and a slow-motion berry.

The added features gave the player more decisions to make. They also introduced more things to track and test, such as item timers, level changes, and obstacle collisions. Asking for “more complex” produced features, but my next improvement should have a specific purpose that I can evaluate.

Stage 4 · A different game

Tag!

I then asked WebbGPT to make a tag game. Its menu offered a computer opponent or two players on one keyboard. The objective was to spend less time as IT during a 60-second round.

Compared with Snake, this game needs to track two players, which one is IT, and how long each player has held that role. It helped me see how changing the game idea changes the information the program needs to remember.

Stage 5 · Another direction

Cube Dash

Finally, I asked for a Geometry Dash-like game. WebbGPT created Cube Dash, with an automatically moving cube, jumping, spikes, attempts, and percentage progress.

This introduced a different movement idea: gravity and jump velocity. The result expanded the kinds of games I had requested, but understanding one smaller game first gives me a manageable starting point for editing code.

Outcome

What my process produced

My requests produced several browser-game prototypes, including an original and repaired Snake game, Snake Deluxe, Tag, and Cube Dash. The screenshots document the blank first version and the later start screens. They do not by themselves prove that every gameplay feature works.

The most useful part of this process was the transition from receiving a game to reporting a problem and requesting a revision. My next step is to make my testing and requests more specific.

Code autopsy · Repaired Snake

1. The canvas

Line 71 of the repaired Snake file places the canvas inside the HTML body, below the score display and above the touch controls: 

<canvas id="game" width="600" height="540"
        tabindex="0"></canvas>

The drawing area is 600 pixels wide and 540 pixels tall. Lines 82–84 get its drawing context and define the grid: 

const canvas = document.getElementById('game');
const ctx = canvas.getContext('2d');
const COLS = 20, ROWS = 18, CELL = 30;

There are 20 columns and 18 rows, with 30-pixel cells. That matches the canvas because 20 × 30 = 600 and 18 × 30 = 540.

Changing only the canvas width or height would not change the grid or its collision boundaries. A smaller canvas could cut off the board, while a larger one could leave unused space. To change the playable board, I would need to keep the canvas, grid dimensions, and cell size consistent.

2. The state variables

The main state variables are declared on lines 95–98 inside the function that wraps the script: 

let snake, dir, apple, score, speed;
let playing, gameOver, started, moveQueue;
let best = Number(storage.get('snakeBest') || 0);
let rafId = null;
let lastTime = 0;

The first declaration is split across two lines here for readability. These values are initialized in reset() or elsewhere in the setup.

Variable What it tracks
snake The grid positions of the head and body.
dir The current movement direction.
moveQueue Direction changes waiting for a movement step.
apple The apple’s position.
score and best The current score and saved best score.
speed The delay between movement steps in milliseconds.
playing, gameOver, started Whether the game is running, ended, or has begun.
rafId and lastTime The scheduled animation frame and last movement time.

One detail I noticed is that speed starts at 140, but a smaller value makes the snake faster. The value represents waiting time, not distance traveled.

3. The game loop

The repeating function is loop(t) on lines 137–144: 

function loop(t) {
  rafId = requestAnimationFrame(loop);

  if (!playing) {
    stopLoop();
    return;
  }

  if (t - lastTime >= speed) {
    lastTime = t;
    step();
  }
}

requestAnimationFrame asks the browser to run the function around its next display refresh. The exact rate depends on the browser and display; it is not a guaranteed fixed number of calls per second.

The two main jobs are updating the game state and drawing the result. In this version, loop() checks the timer first. step() updates movement and checks collisions, then calls draw().

This means the game does not move or redraw on every animation callback. Initially, it waits at least 140 milliseconds between movement steps.

The check if (rafId !== null) return; in startLoop() prevents starting another active loop. stopLoop() cancels the scheduled frame. This connects to the pause/resume issue WebbGPT described.

4. Input handling

The keyboard listener begins on line 274: 

window.addEventListener('keydown', e => {
  // The handler maps arrow keys and WASD to directions.
});

Arrow keys and WASD call startGame() and setDir(map[e.key]). Pressing a direction key does not immediately change the snake’s position. It adds a direction to moveQueue.

During the movement step, the code takes a queued direction and calculates the new head position: 

if (moveQueue.length) dir = moveQueue.shift();

const head = {
  x: snake[0].x + dir.x,
  y: snake[0].y + dir.y
};

The comparison below prevents an immediate reversal: 

if (nd.x === -last.x && nd.y === -last.y) return;

Space or Enter can pause and resume during a game. After game over, either key resets the game to its ready screen, and another start input begins movement. Clicking the board can also start, pause, resume, or reset.

5. Collision and game-over logic

Lines 166–167 compare the new head position with the boundaries and existing snake segments: 

if (
  head.x < 0 ||
  head.x >= COLS ||
  head.y < 0 ||
  head.y >= ROWS ||
  snake.some(s => s.x === head.x && s.y === head.y)
) {
  playing = false;
  gameOver = true;
  stopLoop();
  // The remaining code updates the score and draws the result.
}

The first four comparisons check whether the head is outside the grid. The final comparison checks whether any snake segment occupies the same x and y position as the new head.

When a collision occurs, the program stops movement, sets gameOver to true, and draws the game-over screen.

This version has no explicit win condition. Filling every square is an edge case worth investigating because the apple-placement function would run out of empty spaces. I have not tested or fixed that case yet.

6. Scoring

The score is stored in score, declared on line 95 and reset to zero on line 104. Lines 179–180 detect eating an apple and add a point: 

if (head.x === apple.x && head.y === apple.y) {
  score++;
  updateScore();
  if (speed > 70) speed -= 3;
  placeApple();
}

score++; is the statement that changes the score. updateScore() copies the value into the HTML score display.

Eating also reduces the movement delay, making the snake faster. The snake grows because the eating branch keeps the tail, while a normal movement step removes it.

After a collision, the program compares the current score with best. If the current score is higher, it updates the best score and attempts to save it.

Reflection

What I learned

The game separates what it remembers from what it draws. Input changes a direction queue. The movement step changes positions and checks the rules. Drawing makes the current state visible.

This gives me a way to investigate problems: check whether an input was received, whether the state changed, and whether the screen reflects that change.

I also learned that my feedback should be more specific. Saying “it doesn’t work” helped begin a revision, but recording the browser, the exact action, the visible result, and any console error would provide better evidence.

My next step is to understand and intentionally change one game, then document whether the change improves it.
