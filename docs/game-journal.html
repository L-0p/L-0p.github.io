One Shot, Autopsy, Goals

My process using WebbGPT to create browser games, troubleshoot, and understanding how the code works.

My starting point

I started by asking WebbGPT to make a playable game like Google Snake. I wanted to see how an idea described in a prompt could become a browser game.

The first result did not work when I tried to start it. I reported the problem and asked WebbGPT to revise the game. After that, I asked for a more complex Snake game, a tag game, and a Geometry Dash-like game.

Stage 1 · First prompt

The first Snake game did not start

My first request was: “Can you make a playable game that is like the snake game on Google?”

The page displayed the score and instructions, but the board was blank. There was no visible snake or apple. This was the problem that led me to ask for a revision.

This showed me that receiving generated code does not automatically mean the result works. Trying the game revealed a problem that the original response did not.

Stage 2 · Revision

Asking WebbGPT to make it work

I told WebbGPT, “the game isnt working when i try to start it.” It gave a revised version and explained changes to storage access, starting the game, and managing the game loop.

  • It wrapped localStorage access in try/catch so blocked storage would not stop the script.
  • It added click-to-start and a keyboard listener on window.
  • It tracked and canceled animation frames to prevent duplicate loops during pause and resume.

The screenshot shows a visible improvement from the blank first version, as WebbGPT proposed the causes of the failure.

Stage 3 · More complexity

Snake Deluxe

Next, I asked WebbGPT to make the game more complex. The new version introduced Easy, Normal, and Hard modes, levels, stone obstacles, golden apples, and a slow-motion berry.

The added features gave the player more decisions to make. They also introduced more things to track and test, such as item timers, level changes, and obstacle collisions.

Stage 4 · A different game

Tag!

I then asked WebbGPT to make a tag game. Its menu offered a computer opponent or two players on one keyboard. The objective was to spend less time as IT during a 60-second round.

Compared with Snake, this game needs to track two players, which one is IT, and how long each player has held that role. It helped me see how changing the game idea changes the information needed to create the game; what should be kept and what should be removed.

Stage 5 · Another direction

Cube Dash

Finally, I asked for a Geometry Dash-like game. WebbGPT created Cube Dash, with an automatically moving cube, jumping, spikes, attempts, and percentage progress.

This introduced a different movement idea: gravity and jump velocity. The result expanded the kinds of games I had requested, but understanding one smaller game first gives me a manageable starting point for editing code.

Outcome

What my process produced

My requests produced several browser-game prototypes, including an original and repaired Snake game, Snake Deluxe, Tag, and Cube Dash. The screenshots document the blank first version and the later start screens. They do not by themselves prove that every gameplay feature works.

The most useful part of this process was the transition from receiving a game to reporting a problem and requesting a revision. My next step is to make my testing and requests more specific.

Code autopsy · Repaired Snake

1. The canvas

Line 71 of the repaired Snake file places the canvas inside the HTML body, below the score display and above the touch controls: 

<canvas id="game" width="600" height="540"
        tabindex="0"></canvas>

The drawing area is 600 pixels wide and 540 pixels tall. Lines 82–84 get its drawing context and define the grid: 

const canvas = document.getElementById('game');
const ctx = canvas.getContext('2d');
const COLS = 20, ROWS = 18, CELL = 30;

There are 20 columns and 18 rows, with 30-pixel cells. That matches the canvas because 20 × 30 = 600 and 18 × 30 = 540.

Changing only the canvas width or height would not change the grid or its collision boundaries. A smaller canvas could cut off the board, while a larger one could leave unused space. To change the playable board, I would need to keep the canvas, grid dimensions, and cell size consistent.

2. The state variables

The main state variables are declared on lines 95–98 inside the function that wraps the script: 

let snake, dir, apple, score, speed;
let playing, gameOver, started, moveQueue;
let best = Number(storage.get('snakeBest') || 0);
let rafId = null;
let lastTime = 0;

The first declaration is split across two lines here for readability. These values are initialized in reset() or elsewhere in the setup.

Variable What it tracks
snake The grid positions of the head and body.
dir The current movement direction.
moveQueue Direction changes waiting for a movement step.
apple The apple’s position.
score and best The current score and saved best score.
speed The delay between movement steps in milliseconds.
playing, gameOver, started Whether the game is running, ended, or has begun.
rafId and lastTime The scheduled animation frame and last movement time.

One detail I noticed is that speed starts at 140, but a smaller value makes the snake faster. The value represents waiting time, not distance traveled.

3. The game loop

The repeating function is loop(t) on lines 137–144: 

function loop(t) {
  rafId = requestAnimationFrame(loop);

  if (!playing) {
    stopLoop();
    return;
  }

  if (t - lastTime >= speed) {
    lastTime = t;
    step();
  }
}

requestAnimationFrame asks the browser to run the function around its next display refresh. The exact rate depends on the browser and display; it is not a guaranteed fixed number of calls per second.

The two main jobs are updating the game state and drawing the result. In this version, loop() checks the timer first. step() updates movement and checks collisions, then calls draw().

This means the game does not move or redraw on every animation callback. Initially, it waits at least 140 milliseconds between movement steps.

The check if (rafId !== null) return; in startLoop() prevents starting another active loop. stopLoop() cancels the scheduled frame. This connects to the pause/resume issue WebbGPT described.

4. Input handling

The keyboard listener begins on line 274: 

window.addEventListener('keydown', e => {
  // The handler maps arrow keys and WASD to directions.
});

Arrow keys and WASD call startGame() and setDir(map[e.key]). Pressing a direction key does not immediately change the snake’s position. It adds a direction to moveQueue.

During the movement step, the code takes a queued direction and calculates the new head position: 

if (moveQueue.length) dir = moveQueue.shift();

const head = {
  x: snake[0].x + dir.x,
  y: snake[0].y + dir.y
};

The comparison below prevents an immediate reversal: 

if (nd.x === -last.x && nd.y === -last.y) return;

Space or Enter can pause and resume during a game. After game over, either key resets the game to its ready screen, and another start input begins movement. Clicking the board can also start, pause, resume, or reset.

5. Collision and game-over logic

Lines 166–167 compare the new head position with the boundaries and existing snake segments: 

if (
  head.x < 0 ||
  head.x >= COLS ||
  head.y < 0 ||
  head.y >= ROWS ||
  snake.some(s => s.x === head.x && s.y === head.y)
) {
  playing = false;
  gameOver = true;
  stopLoop();
  // The remaining code updates the score and draws the result.
}

The first four comparisons check whether the head is outside the grid. The final comparison checks whether any snake segment occupies the same x and y position as the new head.

When a collision occurs, the program stops movement, sets gameOver to true, and draws the game-over screen.

This version has no explicit win condition. Filling every square is an edge case worth investigating because the apple-placement function would run out of empty spaces. I have not tested or fixed that case yet.

6. Scoring

The score is stored in score, declared on line 95 and reset to zero on line 104. Lines 179–180 detect eating an apple and add a point: 

if (head.x === apple.x && head.y === apple.y) {
  score++;
  updateScore();
  if (speed > 70) speed -= 3;
  placeApple();
}

score++; is the statement that changes the score. updateScore() copies the value into the HTML score display.

Eating also reduces the movement delay, making the snake faster. The snake grows because the eating branch keeps the tail, while a normal movement step removes it.

After a collision, the program compares the current score with best. If the current score is higher, it updates the best score and attempts to save it.

Reflection

What I learned

The game separates what it remembers from what it draws. Input changes a direction queue. The movement step changes positions and checks the rules. Drawing makes the current state visible.

This gives me a way to investigate problems: check whether an input was received, whether the state changed, and whether the screen reflects that change.

I also learned that my feedback should be more specific. Saying “it doesn’t work” helped begin a revision, but recording the browser, the exact action, the visible result, and any console error would provide better evidence.

My next step is to understand and intentionally change one game, then document whether the change improves it.

Assignment 2: Developing the Tag Game with AI

I used WebbGPT to develop a browser-based tag game and then guided six revisions of it. My process changed from requesting a game to trying the result, noticing specific problems, and asking for targeted improvements. The main challenges were making the computer opponent feel human, creating usable maps, and helping it move around walls without getting stuck or hesitating.

WebbGPT wrote the game code and proposed the technical fixes. I chose the direction, tried the results, reported problems, and asked for changes and explanations. AI also helped organize this journal; I did not create everything in this journal.

From a broad request to specific feedback

I started by asking WebbGPT to make a tag game. The first version offered a computer opponent or two players on one keyboard, with 60-second rounds. Tagging the other player swapped who was IT, and the player who spent less time as IT won. This gave me a basic game to interact with and improve.

My next request focused on how the computer behaved: I wanted a human-like reaction delay and an explanation of the new code. Later, I asked for more maps and better graphics. As I tried the results, my prompts shifted toward concrete problems: the Maze could not be crossed, the computer got stuck against walls, and it hesitated for about 5–10 seconds around corners. Those observations drove the later revisions.

My later feedback was more useful than my original broad requests. Reporting that the Maze could not be crossed pointed toward the layout. Reporting that the computer stuck to walls pointed toward navigation. Reporting 5–10-second hesitation gave a concrete symptom to investigate. I did not have to know the algorithm’s name to describe what was wrong, but asking to see and explain the code helped connect each change to the behavior.

I also encountered a delivery problem when an attachment would not load. WebbGPT supplied fresh HTML and ZIP copies of Tag v7. Those were new download copies of the same code, not additional gameplay improvements. That taught me to separate a problem opening a file from a problem inside the game.

Where my coding understanding deepened

Structure, appearance, and behavior have different jobs. HTML provides elements such as the canvas and score display, CSS controls their appearance, and JavaScript changes the state and draws the game. In Tag, the JavaScript tracks both players, which one is IT, the round timer, and each player’s time as IT. The movement code updates positions, collision checks prevent movement through walls, and drawing displays the current state. A visually polished arena can still have a navigation problem because appearance and movement logic have different jobs.

Time values control different kinds of behavior. The Tag reaction delay is intentional: it makes the opponent wait after being tagged. Getting stuck for several seconds at a corner is a separate problem. In v7, REPLAN_INTERVAL = 0.15 means the route can be reconsidered every 150 ms; it does not mean that the whole game only draws every 150 ms. Learning to distinguish these timers helps me ask for the right change.

Collision detection and navigation are separate problems. Collision logic can stop a player from moving through a wall without telling the player how to go around it. The later Tag versions need both safe positions and safe connections between them. The player’s radius matters because a route that clears a wall for a single point may still scrape it for a circular character.

The way a map is represented changes how a route is found. In v6, the map is represented by a grid of safe positions connected by equal-length steps. Breadth-first search explores those connections. In v7, the important positions are near obstacle corners, and their connections can have different lengths. The code assigns each connection its actual distance:

const cost = Math.hypot(
  navNodes[i].x - navNodes[j].x,
  navNodes[i].y - navNodes[j].y
);

This is the calculation in buildNavigation() in Tag v7, reformatted for readability. The search then compares total travel distance rather than just counting connections. I can explain the reason for that change at a conceptual level; I still need practice implementing these algorithms independently.

Small comparisons can cause visible problems. In v7, aiInput() removes a waypoint when the player is within 0.5 pixels:

while (aiPath.length &&
  Math.hypot(aiPath[0].x - p2.x, aiPath[0].y - p2.y) < 0.5) {
  aiPath.shift();
}

The source explains that arrival thresholds must agree so the opponent does not stop near a waypoint without removing it. This deepened my understanding of debugging: a noticeable delay can come from the relationship between two checks, not simply from a movement-speed value.

What the outcome does and does not prove

The result is a Tag prototype developed through seven versions, with a documented sequence of changes to reactions, maps, and navigation. The chat record reports 80 simulated chase scenarios passing for v7. That is a reported AI test result, not 80 tests that I personally performed, and it does not establish that every live-play situation is bug-free. My reported problems provide evidence of interacting with the results; the source files provide evidence of what changed. The Tag screenshot in the original assignment shows its initial menu; it does not document the later navigation revisions. Those changes are documented by the conversation summary and versioned source code.

AI helped me get prototypes and revisions quickly, but I still had to judge whether the behavior matched my intention. A more elaborate response or more code was not automatically a successful outcome. The progress came from connecting a specific observation to a specific change and then checking the result again.

How I would approach software development next time

  1. Define success before adding features. I would begin with one arena and a small set of checks: start a round, move both players, tag and swap roles, finish the timer, and restart. I would make sure those work before adding more maps or visual effects.
  2. Keep a version and test log. For each change, I would record the prompt, file version, expected behavior, actual behavior, and a screenshot or short recording. That would let me compare versions and return to an earlier one if a revision introduced a problem.
  3. Describe a reproducible problem. Instead of only saying the AI is bad, I would identify the map, player roles, positions, obstacle, and how long the problem lasts. I would ask for one focused change and an explanation of the relevant function.
  4. Retest old behavior after a fix. After changing navigation, I would check both chasing and fleeing on every map, including corners, narrow gaps, and role swaps. I would also check that the intended reaction delay remains. Fixing one scenario should not silently break another.
  5. Use AI explanations to build independence. I would predict what a small code change should do, make or request that change, and compare the result with my prediction. I would keep AI-reported tests separate from my own observations.

A more useful future prompt would be: “On the Maze map, the computer stops at a corner while chasing me. Keep the intended reaction delay, but check whether the waypoint arrival condition prevents it from continuing. Explain the change and test chasing and fleeing around the same obstacle.” This is a proposed future prompt, not a quotation from my earlier chat.

My main takeaway is that software development is an ongoing cycle of defining behavior, trying a result, observing a problem, and revising it. I want to use AI to support that cycle while becoming more capable of explaining and testing the code myself.

Video Game Controller Project: Connecting a Joystick to Tag

My goal and how I used AI

My goal was to control Player 1 in my Tag game with a physical joystick connected to an Arduino. This would extend my earlier game project by connecting a physical input device to the browser game.

I used WebbGPT to write the Arduino code and modify the game. I first asked for a program that would display the joystick’s X and Y readings in the Serial Monitor. Later, I asked it to use those readings to control the Tag player. WebbGPT added a Connect Joystick button and code for receiving data from the Arduino over USB.

WebbGPT wrote the code and suggested troubleshooting steps. My role was to choose what I wanted the controller to do, try the supplied code, and report the problems I encountered. AI also helped organize this journal entry.

My process and the problems I encountered

Using code intended for the wrong device

One problem happened after I asked for C++ code. WebbGPT supplied desktop versions as well as the Arduino code, and I put the Windows desktop version into the Arduino IDE. This produced the error:

windows.h: No such file

When I shared the error with AI, it explained that the Windows version was meant to run on a Windows computer, while the Arduino needed the Arduino sketch.

This helped me understand that identifying a programming language is not enough to know where a program will work. In future prompts, I should specify that I need code to upload to an Arduino, rather than asking only for “C++.”

Encountering a missing brace

Another error was:

expected } at end of input

The chat identified a missing closing brace at the end of loop(). WebbGPT supplied another copy with braces on separate lines and suggested using Auto Format to check their structure.

I learned that braces define where a block of code starts and ends. Losing one while copying code can prevent the whole program from compiling. This also showed me why formatting matters, as indentation makes the structure easier to inspect when something goes wrong.

The later screenshot in my chat showed a successful compile. However, compiling successfully did not prove that the program had been uploaded or that the joystick could control the game.

The joystick still did not move the player

After the game was modified for joystick input, I reported that moving the joystick did not move the character.

WebbGPT responded with a diagnostic version of the game that displayed incoming joystick readings and the values used by the game. It also suggested checking the browser, closing the Serial Monitor, and confirming the correct Arduino sketch and communication speed.

I did not complete those diagnostic checks, so I cannot identify the cause of the connection problem. My outcome was an unfinished controller integration, with code and a diagnostic tool available but no confirmed joystick-controlled gameplay.

What I learned about troubleshooting

This project helped me distinguish between several different signs of progress:

  • Compiling: The code passes the compiler’s checks.
  • Uploading: The program is transferred to the Arduino.
  • Receiving data: The browser receives readings from the Arduino.
  • Controlling the game: The game uses those readings to move the character.

Success at one stage does not automatically prove that the next stage works.

My original report—“the joystick does not move the character”—described the visible problem, but it did not show where the process stopped. A more useful next question would be: Does the browser receive changing X and Y values when I move the joystick?

If no values arrive, I would investigate uploading and the connection. If values arrive but do not change, I would investigate the joystick readings and wiring. If the values change but the character does not move, I would investigate how the game handles those values.

These are my planned next steps, not tests I have already completed.

How I would approach a future project

Next time, I would test the project in smaller stages before connecting everything. I would first confirm that the Arduino reads the joystick, then confirm that the browser receives the readings, and finally test movement in the game.

I would also keep a troubleshooting log with the exact error, my explanation of what might be wrong, the AI suggestion I tried, and the result. This would make my own decisions clearer and help me avoid changing several things without knowing which change mattered.

My next goals

  1. Check that the physical wiring between the joystick, breadboard, and Arduino is correct.
  2. Confirm that the correct Arduino sketch uploads successfully and save evidence of the result.
  3. Record the diagnostic readings with the joystick centered and moved in each direction.
  4. Use those observations to choose one focused troubleshooting step, then repeat the same test.

The project did not reach working joystick control, but it gave me a clearer understanding of the difference between generating code and verifying a complete system. In future projects, I want to use AI not only to produce code, but also to help me design tests whose results I can observe and explain myself.
